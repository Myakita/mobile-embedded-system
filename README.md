## Назначение и пользователи

Приложение предназначено для оператора или руководителя подразделения, которому нужно видеть состояние и последнее известное местоположение участников, понимать актуальность данных и отправлять разрешённые команды.

Основная проблема — разрозненная информация при нестабильной связи. Пользователь должен отличать свежие данные от устаревших, понимать, от какого устройства поступили показатели, и видеть результат своих действий.

Основные пользователи:

- **Оператор / руководитель:** наблюдает за участниками, просматривает показатели и карту, отправляет разрешённые команды.
- **Настройщик:** подготавливает сеть, связывает устройства с пользователями и задаёт параметры подключения.
- **Участник с устройством:** источник телеметрии; постоянная работа с интерфейсом приложения от него не требуется.

## Функциональный объём

Целевые сценарии мобильного приложения:

1. Выбор сети и просмотр её участников и устройств.
2. Просмотр телеметрии: температуры, пульса, давления и времени последнего обновления.
3. Отображение положения и направления движения на карте, качества и давности позиции.
4. Приём сообщений, обработка повторов и отображение состояния подключения.
5. Отправка команд разрешённым получателям с понятным статусом передачи.
6. Сохранение необходимых данных и настроек при перезапуске приложения.

Этот перечень описывает продуктовый объём, а не подтверждает завершённость всех функций. Готовность определяется проверками и критериями приёмки.

## MVP и документация

Для проекта ранее подготовлены пользовательские истории, критерии приёмки, приоритизация MoSCoW и предварительный план на 3,5 месяца. Они относятся к общей системе и служат исходным материалом для выделения мобильного MVP.

Для этой дисциплины Product Owner и аналитик уточняют мобильный backlog, а тимлид и разработчик оценивают реализацию. Оценки и распределение работ команды общей системы не переносятся автоматически на текущую команду.

Минимальный сквозной сценарий: подключиться к тестовому источнику → получить телеметрию → открыть карточку и карту → отличить актуальные данные от устаревших → отправить разрешённую команду → проверить поведение при потере и восстановлении связи.

Приоритеты MoSCoW:

- **Must:** функции, без которых этот сценарий нельзя пройти и принять.
- **Should:** важные дополнения после готовности обязательного сценария.
- **Could:** улучшения при наличии времени.
- **Won’t this time:** функции, исключённые из текущего выпуска.

Перед приёмкой для каждой обязательной истории должны быть определены ожидаемый результат и способ проверки. Кандидат в выпуск сопровождается результатами автотестов и ручного прогона.

## Технологии

По текущей конфигурации Android-проекта:

- Java 17, Android SDK, View Binding.
- MapLibre Native для карты.
- Room для локального хранения.
- ViewModel и LiveData для состояния интерфейса.
- Eclipse Paho для MQTT.
- Gradle Wrapper для сборки; JUnit и Espresso подключены для тестирования.

## Граница дисциплины

Предмет работы этой команды — мобильное приложение, его требования, разработка, сборка и проверка качества. Edge-устройства, виртуальная периферия и MQTT-брокер рассматриваются как внешние компоненты или тестовые зависимости.

Разработка embedded-части, Yocto-образа и инфраструктуры общей системы описывается отдельно. Тестовое окружение приложения может использовать их готовые артефакты. Прикладной backend не является обязательной частью мобильного MVP.

Состав и роли команды в этом README относятся только к дисциплине мобильного приложения и отличаются от распределения ответственности в ветке `main`.
