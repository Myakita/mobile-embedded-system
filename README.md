## 2. Состав репозитория

Основной репозиторий остаётся местом для embedded-части, инфраструктуры и эмулятора. Подмодулями вынесены только независимые компоненты с собственной историей:

```text
.
├── emulator/      # интеграционный эмулятор и сценарии его проверок
├── protocol/      # общий контракт сообщений и тестовые векторы
└── mobile_app/    # самостоятельный Android-проект
    └── protocol/  # тот же закреплённый контракт для Android
```

- `emulator/` — обычный каталог в этом репозитории. Он собирает embedded, MQTT и мобильный клиент в интеграционные сценарии; отдельным подмодулем не является.
- `protocol/` — подмодуль [mobile-embedded-system-protocol](https://github.com/Myakita/mobile-embedded-system-protocol). Здесь живут бинарная спецификация, правила MQTT и общие тестовые векторы.
- `mobile_app/` — подмодуль [mobile-embedded-system-mobile-app](https://github.com/Myakita/mobile-embedded-system-mobile-app). Его `protocol/` закреплён на версии контракта, с которой проверено приложение.

Клонирование полной системы:

```bash
git clone --recurse-submodules https://github.com/Myakita/mobile-embedded-system.git
```

Для существующего клона используйте `git submodule update --init --recursive`.

Версию протокола изменяют в отдельном репозитории. После прохождения общих векторов embedded и Android обновляют свои указатели `protocol/`; затем в этом репозитории отдельно обновляется указатель `mobile_app/`. Ветки и репозитории не сливаются между собой.

## 3. Предметная область

Проект представляет собой распределённую систему мониторинга состояния и местоположения пользователей, оснащённых автономными телеметрическими устройствами.

Каждое устройство собирает и передаёт:

1. серийный номер устройства;
2. идентификатор пользователя;
3. температуру;
4. пульс;
5. систолическое и диастолическое давление;
6. положение, рассчитанное по данным GNSS + IMU;
7. направление движения;
8. оценку качества рассчитанной позиции.

Система поддерживает два прикладных типа сообщений:

```text
TELEMETRY
COMMAND
```

Телеметрия передаётся к разрешённым вышестоящим получателям, команды — в обратном направлении к разрешённым нижестоящим получателям.

Организационная иерархия существует на уровне мобильного приложения. Устройство не должно хранить семантику организационной структуры: название подразделения, должность или роль пользователя.

Устройство получает только необходимые идентификаторы, список допустимых получателей и готовые сетевые параметры.

## 4. Общая архитектура

Система строится как многоканальная сеть с единым прикладным форматом сообщений.

```text
                    Sensors / GNSS / IMU
                            │
                            ▼
                      прикладное сообщение
                            │
                            ▼
                         RouterD
                  ┌─────────┼─────────┐
                  │         │         │
                  ▼         ▼         ▼
                LoRa      Wi‑Fi      LTE
                  │         │         │
                LMesh      MQTT      MQTT
                  │         │         │
                  └─────────┼─────────┘
                            │
                         Multimesh
                            │
                      MQTT Broker
                            │
                            ▼
                      Android application
```

Основной принцип: **данные отделены от транспорта**. Прикладной backend не входит в MVP. MQTT-брокер остаётся транспортной инфраструктурой; локальное прямое соединение приложения с устройством работает без внешнего брокера. CI/CD и сборочная инфраструктура не участвуют в обмене пользовательской телеметрией.

Один и тот же логический пакет может быть доставлен через LoRa, Wi‑Fi или LTE без изменения его источника, получателя и номера последовательности.

## 5. Edge-устройство

Edge-узел представляет собой Linux-устройство, эмулирующее Raspberry Pi с набором виртуальных периферийных устройств.

Основные задачи edge-части:

1. эмуляция периферии;
2. сбор телеметрии;
3. объединение GNSS + IMU;
4. формирование единого `прикладное сообщение`;
5. передача сообщений через LoRa, Wi‑Fi и LTE;
6. приём входящих команд;
7. дедупликация сообщений;
8. конфигурирование сетевых интерфейсов и периферии через мобильное приложение.

### 4.1. Эмулируемая периферия

Предполагаются следующие интерфейсы:

```text
SPI   → IMU
I²C   → Barometer
UART  → GNSS, NMEA
LTE   → LTE modem
GPIO  → цифровые входы/выходы
```

Для тестирования периферии допускаются Linux-механизмы виртуализации устройств, mock-драйверы и UMockdev там, где это применимо.

### 4.2. GNSS

GNSS-устройство взаимодействует по NMEA.

В системе не закладывается зависимость от конкретного производителя GNSS-модуля.

### 4.3. Позиционирование

Устройство формирует итоговую позицию на основе GNSS + IMU.

Мобильное приложение получает уже рассчитанные:

```text
latitude
longitude
heading
positionQuality
```

Повторное sensor fusion в Android-приложении не требуется.

## 6. Дедупликация

Уникальность сообщения определяется как:

```text
MessageID = deviceSerial + sequence
```

Если одно сообщение поступило несколькими путями, например:

```text
Wi‑Fi
LTE
LoRa → gateway → MQTT
```

оно должно быть обработано только один раз.

Дедупликация выполняется:

- на промежуточных узлах, где это необходимо;
- в Android-приложении при прямом или параллельном получении сообщения.

## 7. LoRa mesh

Для LoRa используется собственный компактный протокол поверх raw LoRa PHY.

Классический LoRaWAN не является основой mesh-архитектуры.

Логическая схема:

```text
LoRa PHY
   ↓
LMesh
   ↓
прикладное сообщение
```

Устройства могут ретранслировать сообщения между соседними узлами.

### 7.1. Минимальный набор LMesh-сообщений

```text
HELLO
DATA
ACK
```

| Тип | Назначение |
|---|---|
| `HELLO` | Обнаружение доступного соседнего узла |
| `DATA` | Передача `прикладное сообщение` |
| `ACK` | Подтверждение сообщения, если оно требуется |

Динамический поиск маршрутов через `ROUTE_REQ`, `ROUTE_REPLY` и `ROUTE_ERROR` в текущую модель не входит.


### 7.2. TTL

`ttl` ограничивает число дальнейших пересылок и предотвращает бесконечное хождение пакета по сети.

---

## 8. Wi‑Fi и LTE

Wi‑Fi и LTE являются IP-транспортами.

Для обоих используется MQTT.

```text
прикладное сообщение
       ↓
      MQTT
       ↓
      TCP/TLS
       ↓
   Wi‑Fi или LTE
```

Отдельный application protocol для LTE не требуется.

Для Linux LTE-модем должен рассматриваться как сетевой интерфейс, например `wwan0`.

Для Raspberry Pi предпочтительно USB-подключение LTE-модема с MBIM/QMI/ModemManager.

---

## 9. MQTT

В системе используется единое сетевое MQTT-пространство каждой мультисети.

Отдельные `local/...` topics не используются.

Структура MQTT topics не должна быть жёстко зашита в устройство.

Она формируется мобильным приложением на основании:

- выбранной мультисети;
- положения пользователя в иерархии;
- источника сообщения;
- получателя;
- типа сообщения.

Базовая модель:

```text
<network_root>/<hierarchy_path>/<message_type>/to/<destination_id>/from/<source_id>
```

### 9.1. Телеметрия

```text
<root>/<hierarchy>/telemetry/to/<dst>/from/<src>
```

### 9.2. Команды

```text
<root>/<hierarchy>/command/to/<dst>/from/<src>
```

Устройство получает от приложения уже готовые:

```text
network_root
hierarchy_path
publish_topics[]
subscribe_topics[]
allowed_destination_ids[]
```

Устройство не обязано интерпретировать смысл `hierarchy_path`.

### 9.3. QoS

Базовая политика:

```text
TELEMETRY → QoS 0
COMMAND   → QoS 1
```

MQTT QoS не заменяет application-level дедупликацию через `deviceSerial + sequence`.

## 10. Иерархия

Иерархия настраивается и хранится в мобильном приложении. В MVP одну мультисеть конфигурирует один назначенный клиент; автоматическая синхронизация конфигурации между приложениями не требуется.

Пример:

```text
Root
 │
 ├── Level A
 │    ├── User A
 │    └── User B
 │
 └── Level B
      └── User C
```

Для устройства узлы иерархии представлены непрозрачными ID.

Приложение определяет:

- кому пользователь отправляет телеметрию;
- кому пользователь имеет право отправлять команды;
- какие MQTT topics публиковать;
- на какие MQTT topics подписываться;
- какие `destinationId` разрешены.

Изменение иерархии не должно требовать перепрошивки устройства.

## 12. Прямое подключение приложения к устройству

Мобильное приложение поддерживает обмен через MQTT-брокер и прямое подключение к edge-устройству без прикладного сервера.

Допустимые варианты:

```text
Android App
    │
  Wi‑Fi
    │
Edge Device
```

и при наличии подходящей сетевой доступности:

```text
Android App
    │
   LTE/IP
    │
Edge Device
```

Прямое соединение используется для:

- получения телеметрии;
- настройки устройства;
- передачи разрешённых команд;
- диагностики;
- работы при недоступности внешнего MQTT-брокера, если транспорт позволяет установить соединение.

Полученная напрямую телеметрия должна:

1. отображаться в приложении;
2. дедуплицироваться по `deviceSerial + sequence`;
3. сохранять идентичность логического сообщения при повторном получении через MQTT; обязательная пересылка в backend не требуется.

## 13. MapLibre Native

MapLibre Native используется для отображения:

- текущего положения пользователей;
- направления движения;
- качества позиции;
- времени последнего обновления;

Приложение должно поддерживать:

```text
CURRENT
STALE
UNKNOWN
```

для состояния позиции.

Старая координата не должна отображаться как актуальная без соответствующей индикации.

## 14. Шифрование

Шифрование полезной нагрузки задаётся независимо на стороне устройства и на стороне приложения-получателя.

```text
DEVICE
  └── crypto configuration задаётся отдельно

RECEIVER APP
  └── CryptoProfile задаётся отдельно
```

Приложение должно поддерживать выбор только стандартных алгоритмов.

Допустимые варианты профиля:

```text
AES-128-GCM
AES-256-GCM
ChaCha20-Poly1305
```

Конкретный список должен соответствовать возможностям edge-устройства.

На стороне Android секретный материал должен храниться через Android Keystore или защищённый им механизм.

Ключи не должны храниться открытым текстом в:

```text
SharedPreferences
resources.xml
BuildConfig
обычном JSON
исходном коде
```

При ошибке расшифрования приложение должно различать минимум:

```text
UNKNOWN_KEY
DECRYPTION_FAILED
AUTHENTICATION_FAILED
UNSUPPORTED_CRYPTO
```

Application-level encryption не отменяет TLS для MQTT поверх Wi‑Fi/LTE.

## 15. Инфраструктура, Yocto и проверка качества

Часть B отвечает за воспроизводимую сборку, запуск и проверку продукта. Отдельный прикладной сервер, REST API, серверный ingest и централизованное хранилище телеметрии в MVP не разрабатываются.

Зона ответственности `@Myakita`:

1. CI: сборка edge-компонентов и Android-приложения, запуск автоматических проверок изменений, публикация отчётов и журналов.
2. Yocto: фиксация версий слоёв и конфигурации сборки, рецепты упаковки edge-приложения, минимальный Linux-образ для выбранной QEMU-машины, загрузка образа и запуск сервисов.
3. Стенд: запуск нескольких эмулируемых узлов, тестового MQTT-брокера с TLS и правилами доступа, управление тестовыми данными и сбоями каналов.
4. Интеграционные тесты эмулятора: виртуальная периферия → edge → транспорт → принимающее приложение; проверка команд, повторов, TTL, смены доступного канала и восстановления соединения после сбоев.
5. Автотесты: организация запуска модульных, контрактных и интеграционных тестов; разработчики edge и Android пишут тесты своей логики, инфраструктура объединяет их в обязательные проверки.
6. Ручные тесты: план приёмки и регрессии, проверка интерфейса и карты, протокол результатов и дефектов; проверки выполняются совместно с разработчиками компонентов.
7. CD: публикация версионированных APK, образов, контрольных сумм и отчётов, развёртывание прошедшего проверки образа на тестовом стенде и возврат к предыдущей версии.

Yocto используется для образа эмулируемого Linux-узла. Точная аппаратная эмуляция Raspberry Pi, собственный BSP и прошивка реальных устройств не входят в этот пилот. Версия Yocto, целевая QEMU-машина и ресурсы Linux-runner выбираются и проверяются в первые две недели.

Быстрые проверки запускаются на pull request и push в основную ветку. Полная сборка Yocto и интеграционные проверки образа выполняются при изменении образа/edge/стенда, перед выпуском и по расписанию. Провал обязательной проверки блокирует выпуск. Ручные проверки сохраняются отдельно и не заменяются зелёным CI.

## 18. Синхронизация конфигурации

Необходимо различать сохранение конфигурации в приложении и её применение на устройстве:

```text
APP → локальное хранилище приложения
APP → DEVICE
```

Изменение иерархии, MQTT-параметров, разрешённых получателей и сетевых настроек должно приводить к формированию новой версии конфигурации устройства.

Приложение показывает сохранённую и подтверждённую устройством версии, ожидание применения и ошибку. Локальное сохранение не считается успешным применением на устройстве. Правила доступа проверяются устройством и MQTT-брокером на соответствующих путях; изменение брокерных ACL применяется отдельным шагом инфраструктурной настройки до объявления новых прав действующими.
