# CI (общий репозиторий)

Инфраструктура из [issue #2](https://github.com/Myakita/mobile-embedded-system/issues/2).
Приложение также имеет собственный пайплайн; здесь проверяется ровно тот его
коммит, который закреплён в `mobile_app/`.

## Что уже работает

`.github/workflows/ci.yml` запускается при каждой отправке изменений и открытии PR, если они затрагивают `emulator/`, `rpi-app/`, `tests/`, `Makefile`, корневой `CMakeLists.txt`,
`ci/`, `.clang-format`, указатели `mobile_app`/`protocol` или сам сценарий CI. Изменение только `docs/`
CI не запускает. Ничего не блокирует технически — отправка изменений напрямую в `main` проходит всегда, красный статус
на коммите — сигнал, а не преграда.

Три параллельные джобы:

- **`build`** — `make build test`: CMake-сборка из корневого `CMakeLists.txt` — `emulator/` (библиотека `periph` из четырёх
  `interface/*.cpp`) и edge-сервис `rpi-app/` (бинарь `edge`: CAN — строка телеметрии на кадр; UART — кадры LMash v1
  в MQTT, #22) — и `ctest` (сейчас: `telemetry` — формат строки, без привилегий; `errors` — привилегий не требует, проверяет пути отказа
  `open()` на всех четырёх интерфейсах и безопасность move; `uart_pty` — гоняет UART через pty-пару;
  `broker_config` и `lmash` — разбор конфига брокера и построение MQTT-топика по заголовку кадра), затем
  `make e2e`: сценарии `tests/e2e/*.json` с edge на раннере и настоящим брокером с TLS+ACL (см.
  [TESTING.md](TESTING.md)); лог и `junit.xml` — артефакт `e2e-host-logs`.
- **`guard`** — `python3 ci/guard.py`: форма кода, не объём. См. ниже.
- **`android`** — на закреплённом `mobile_app/` запускает JVM-тесты, lint и сборку
  debug APK. Артефакт `pinned-android-check` содержит APK, отчёты и `revisions.txt`
  с SHA основного репозитория, приложения и обеих копий протокола. Для этой job
  используется JDK 25 и Android SDK 37; результаты хранятся 14 дней.

## Локальное воспроизведение

```bash
git submodule update --init --recursive
make check          # локальные build + test + guard для эмулятора
```

Для проверки закреплённого Android-приложения отдельно выполните из `mobile_app/`
`bash ./gradlew --no-daemon testDebugUnitTest lintDebug assembleDebug` с JDK 25 и Android SDK 37.

Полная сборка эмулятора требует Linux (`libgpiod` v2 через `ci/install-libgpiod-v2.sh`, ядерные заголовки
`linux/can.h`, `linux/i2c-dev.h` — их нет на macOS). На маке то же, что делает `ci.yml`, запускает

```bash
make docker-check   # build + test + guard + e2e в ubuntu:24.04 (ci/dev.Dockerfile), нативный arm64
```

Первый запуск собирает образ с libgpiod v2 и сразу гоняет проверки (~1.5 мин всего), дальше образ берётся из кэша Docker. Модулей ядра в
Docker Desktop нет, поэтому `make devices` так не проверить: его проверяет `full.yml`.
Состав интеграционных тестов и уровни проверки — в [TESTING.md](TESTING.md).

## `ci/guard.py` — почему без бюджетов по строкам

Ранний вариант этого файла держал лимиты строк по каталогам и список разрешённых каталогов верхнего
уровня. От них отказались: они требуют подкручивания ровно тогда, когда проект растёт, то есть
постоянно, и это слишком дорого для учебного проекта. Вместо объёма гейт контролирует **форму** —
семь проверок, которые либо верны всегда, либо не нужны вовсе, без файла-конфига:

| Проверка | Что делает |
|---|---|
| `format` | `clang-format --dry-run --Werror` по `.clang-format`. `make fmt` чинит. |
| `duplicates` | Свой, без сторонних инструментов: хэширует тело каждой функции (границы строк — из `lizard`) и ловит буквальную копипасту между разными функциями. Не ловит копию с переименованными переменными — осознанное ограничение, ловит именно сценарий `uart_v2.cpp` рядом с `uart.cpp`. |
| `complexity` | `lizard -w` (только нарушения, в формате предупреждений clang) с порогами `MAX_FUNCTION_LINES=80`, `MAX_CCN=15`. Уважает `// #lizard forgives` **внутри тела функции** (не над сигнатурой — иначе не работает). Две функции в `uart.cpp` помечены так осознанно: таблица бодрейтов и последовательная настройка `termios` — легитимно длинные/ветвящиеся, не слоп. |
| `file-length` | Файл длиннее `MAX_FILE_LINES=600` строк — падение. Защита от файла на тысячи строк, не инструмент управления объёмом. |
| `orphan-files` | `.cpp` вне всех `CMakeLists.txt` или `.hpp`, который никто не инклюдит и не собирает. |
| `paired-tests` | Для каждого `interface/X.cpp` — хоть один файл в `tests/` инклюдит `interface/X.hpp`. Не требует одного файла теста на один интерфейс: `test_errors.cpp` осознанно покрывает все четыре сразу. |
| `dependency-allowlist` | `pkg_check_modules`/`find_package`/`FetchContent_Declare` вне блока `# guard:deps:start` / `# guard:deps:end` в том же `CMakeLists.txt` — падение. Новая зависимость — однострочный ревьюируемый diff, а не побочный эффект PR с фичей. |
| `submodule-pointers` | Указатель `protocol`/`mobile_app` должен быть предком (или верхушкой) `origin/main` своего репозитория — иначе он либо не запушен, либо потерян при rebase. **Важно:** `git ls-remote <url> <sha>` для этого не годится — `ls-remote` matches ref *names*, не содержимое коммита, и молча возвращает пусто даже для реально запушенного коммита. Проверка идёт через `git fetch` + `merge-base --is-ancestor` внутри уже инициализированного сабмодуля. |
| диффstat (не блокирует) | Таблица «+добавлено/-удалено» по каталогам в `$GITHUB_STEP_SUMMARY`. Только показывает рост, не судит его. |

Три числовые константы (`MAX_FILE_LINES`, `MAX_FUNCTION_LINES`, `MAX_CCN`) — в шапке `ci/guard.py`,
трогать раз в семестр, не на каждый PR.

## `ci/install-libgpiod-v2.sh` — почему он есть

`emulator/interface/gpio.cpp` использует **libgpiod v2** C++ API (`chip::prepare_request()`,
`line_settings`). Ubuntu 24.04 в apt даёт только v1.6, где этого API нет вообще. Скрипт идемпотентен:
проверяет версию через `pkg-config` и, если она младше 2.0, собирает `v2.3.1` из исходников (Meson,
не autotools — актуальная ветка libgpiod перешла на Meson). На реальном GitHub-раннере занимает
десятки секунд; локально на Linux, где v2 уже стоит, пропускается мгновенно.

## `full.yml` — виртуальная периферия и MQTT-стенд, по тегу

Не идёт при каждой отправке изменений — дороже и завязан на вещи, которые ломаются не по вине кода. Триггер:

```bash
git tag full-1 <sha> && git push origin full-1     # без ветки, на любом существующем коммите
git push origin :refs/tags/full-1                  # удалить тег после прогона, если не нужен
```

Плюс еженедельно по расписанию (понедельник, 03:00 UTC) и вручную через `workflow_dispatch`, чтобы не
протухал незаметно, если тег никто не пушит месяцами.

Две независимые джобы:

- **`devices`** — `make devices` (`ctest -L devices`, `emulator/tests/test_devices.cpp`): CAN
  loopback на `vcan0` (`CAN_RAW_LOOPBACK`+`CAN_RAW_RECV_OWN_MSGS`, без внешнего собеседника), запись
  и чтение регистра на `i2c-stub` (бюс ищется по имени адаптера в `/sys/bus/i2c/devices/*/name`,
  номер не детерминирован), GPIO write+read на `gpio-sim` (чип берётся из configfs-атрибута
  `bank0/chip_name`, назначается ядром динамически). Требует root и ядерные модули — **непроверяемо
  локально на macOS/Docker Desktop**, проверяется только на раннере (зелёный с `full-8`): у LinuxKit-ядра там просто нет `/lib/modules`, `modprobe`
  ни для одного из трёх модулей не находит их вообще. Джоба идёт с `continue-on-error: true` —
  `linux-modules-extra-$(uname -r)` на раннере может разойтись с ядром сразу после обновления
  образа, и это не должно портить `full`, пока не станет ясно, что нестабильность реальная.
- **`stand`** — `make stand` (`emulator/stand/smoke.sh`): поднимает `eclipse-mosquitto` с TLS
  (самоподписанный CA, генерируется заново при каждом запуске в `generated/`, не коммитится) и ACL
  (у пользователя `authorized` есть `mes/smoke/#`, у `stranger` нет ничего). Конфиг брокера, ACL,
  сертификаты и пароли генерирует `emulator/stand/lib.sh` из `emulator/stand/stand.env` — это единственное
  место, где записаны порт, пользователи и корень топиков; статических `acl.conf`/`mosquitto.conf` нет. Публикует
  `wireHex` из `protocol/vectors/telemetry-v1.json`, сверяет байт в байт у `authorized`-подписчика,
  затем двумя отдельными проверками — что `stranger` не получает **и** не может опубликовать в тот
  же топик. Проверка ACL идёт по факту доставки, а не по коду завершения клиента: у QoS 0 нет подтверждения, так что
  запрещённая публикация через `mosquitto_pub` всё равно выглядит успешной — значение имеет только то,
  доходит ли сообщение до подписчика. Не требует ядерных модулей, работает в пользовательском пространстве — проверено
  сквозным локальным прогоном, включая намеренную порчу ACL для подтверждения, что скрипт ловит
  регрессию.

Оба джоба впервые прошли целиком на реальном раннере на теге `full-8` (до этого — восемь
итераций, каждая из которых была зелёной локально на macOS и падала в CI). Все причины — одного
класса: **Docker Desktop на маке ведёт себя не так, как нативный Docker на Linux**, и локальный
прогон этого не покажет. Если стенд или `devices` снова начнут падать только в CI — сначала
проверьте эти пять пунктов:

| Что | На маке | На Linux-раннере | Как сделано |
|---|---|---|---|
| Файл, записанный root-контейнером в подключённый каталог | принадлежит хостовому пользователю | принадлежит **root**, хостовый `chmod`/чтение без прав root не работают | root-контейнер не нужен: `lib.sh` пишет файлы от хостового пользователя (хеши паролей считает `python3`, не `mosquitto_passwd`) |
| Демон `mosquitto` | читает конфиг как есть | **дропает привилегии до uid 1883** посреди разбора конфига: `cafile`/`certfile` читаются до дропа, `password_file` — после | всё в `generated/` делается `a+rX` до старта брокера |
| DNS имени сервиса compose из отдельного `docker run --network` | резолвится | `Unable to connect (Lookup error)` | клиенты заходят в net-namespace брокера (`--network container:<id>`) и стучатся в `localhost` |
| Имя узла в TLS-сертификате | — | при `-h localhost` нужен SAN, `CN=broker` не спасает | SAN `DNS:broker,DNS:localhost,IP:127.0.0.1,IP:::1,IP:10.0.2.2` через `-extfile` (работает и с LibreSSL); `10.0.2.2` — так хоста видят гость QEMU и Android-эмулятор |
| `mount -t configfs`, `/dev/i2c-*`, `/dev/gpiochip*` | недоступно вовсе (LinuxKit без модулей) | configfs **уже смонтирован** (`mount` → код 32); узлы устройств доступны только root и группе | `mountpoint -q \|\| mount`; `sudo make devices` |

Отдельная грабля самого macOS: системный `openssl` — это **LibreSSL**, у него нет `-copy_extensions`
и части других флагов настоящего OpenSSL; поэтому в `lib.sh` только пересечение двух наборов. Ещё одна
разница: LibreSSL строит имя файла серийных номеров из пути к CA, обрезая по **первой** точке, и в домашнем
каталоге вида `/Users/имя.фамилия/` пытается писать `/Users/имя.srl`; поэтому `-CAserial` задан явно.

Когда появится C++-кодек протокола, туда же добавится джоба соответствия векторам (кодирование полей
→ `wireHex` и обратно) — в этом заходе не реализовано.

## Yocto + QEMU: базовый образ (#18)

Статус: **работает.** Прогон `image.yml` `37316925361` (коммит `20a7f55`) собрал образ и загрузил
его в QEMU до `qemux86-64 login:`; лог загрузки — артефакт `yocto-boot` этого прогона.
Сборка и загрузка возможны только на Linux-раннере.

- **Версии:** Yocto 5.0 LTS (scarthgap), `poky` закреплён на коммите тега `yocto-5.0.20`, сборщик `kas` 5.5.
  Всё в `yocto/kas.yml`; обновлять коммит отдельным изменением. Ниже 5.0.20 не опускаться — см. ниже.
- **Прогон 1 (`37283095672`, на 5.0.14):** час сборки, затем `linux-libc-headers:do_package` упал в
  `perform_packagecopy`: `tar -xf` под pseudo — `got *at() syscall for unknown directory, fd 4`.
  Причина: `tar 1.35+dfsg-3ubuntu0.4` в Ubuntu 24.04 (security-обновление) открывает каталоги через
  `openat2`, а pseudo в 5.0.14 его не перехватывает. Обёртка `openat2` есть в pseudo из 5.0.20.

  не вызывает `openat2`, так что зелёный результат в такой эмуляции ничего не доказывает.
  Диск ни при чём. `tar-native` вместо обновления не нужен.
- **Прогон 2 (`37291828702`, на 5.0.20):** образ собрался за 3 ч 25 мин (12319 с, без кэша),

  `runqemu` путь к `core-image-minimal-qemux86-64.rootfs.qemuboot.conf` напрямую.
- **Прогон 3 (`37315901621`):** отменён — `apt-get install` повис на `qemu-system-x86` с зеркала

- **Прогон 4 (`37316925361`): зелёный.** Сборка 136 с (sstate совпал на 99%), весь прогон ~8 мин,

- **CI:** `image.yml`: `workflow_dispatch`, дважды в неделю (пн, чт 04:00 UTC: раз в неделю
  попадало бы ровно на 7-дневное удаление неиспользуемого кэша) и по push, если менялось то, что
  попадает в образ (см. «Сценарии в образе»). Таймаут 300 минут. Расписание GitHub отключает в
  публичном репозитории после 60 дней без активности: тогда кэш протухнет, и следующая сборка
  будет холодной (~3.5 ч).
  Раннер закреплён на `ubuntu-24.04` (и в `stand.yml`): 2026-10-29 `ubuntu-latest` переехал на
  26.04, где нет пакета `liblz4-tool`, и плановый прогон упал на `apt-get install` (run
  40858754607). scarthgap проверен на хостах до 24.04, поэтому раннер меняется вместе с poky.
  В summary прогона пишутся CPU, RAM, свободный диск, время сборки и наличие KVM.
  **Ресурсы раннера** (`ubuntu-24.04`, публичный репозиторий): диск `/` 145 GB, после шага
  «Free disk space» свободно 105 GB; KVM доступен. Холодная сборка (без кэша, 1854 задачи sstate)
  — 12319 с ≈ 3 ч 25 мин, укладывается в таймаут 300 минут; с кэшем — ~2 мин.
  Кэш (`downloads` + `sstate`) — 9.2 GiB, почти весь лимит кэша репозитория в 10 GB.
  Кэш `.yocto-cache` сохраняется и после падения (`cache/restore` + `cache/save` с `if: always()`,
  ключ с `run_id`): иначе каждая попытка заново тратит час на native-инструменты. Пустой кэш
  (sstate не записан) не сохраняется, а после сохранения остальные `yocto-*` удаляются — иначе
  две копии по 9 GB вытеснили бы кэши Gradle у Android.
- **Кэш и лимит 10 GB:** sstate в Yocto только растёт — после правки рецепта старые объекты
  остаются. Поэтому после успешной сборки шаг «Prune sstate to this build» запускает
  `poky/scripts/sstate-cache-management.py --stamps-dir=build/yocto/tmp/stamps`: `build/yocto`
  в каждом прогоне свежий, и его stamps — ровно то, что нужно этой сборке. После упавшей сборки
  обрезки нет (stamps неполные). В summary пишутся размеры `sstate` и `downloads` по отдельности
  и предупреждение от 8 GB; `downloads` не обрезается — если упрётся, следующий шаг там.

## Edge-сервис в образе (#24)

Статус: **работает.** Прогон `image.yml` `37320801772` (коммит `945ac57`): в логе загрузки
`vcan: Virtual CAN interface driver`, `Starting edge on vcan0`, `edge: listening on vcan0`, затем
`login:`. Сборка 1317 с (≈22 мин): из sstate не нашлось 34 задачи из 1879 — ядро, libgpiod,
iproute2, `edge`. Обрезка sstate удалила 3151 из 6025 файлов, кэш 9.2 → 7.8 GiB.

- **Слой `yocto/meta-mes`:** подключён в `kas.yml` как репозиторий без `url` (этот же репозиторий).
  Рецепт `edge.bb` собирает цель `edge` корневого CMake из checkout этого репозитория:
  `SRC_URI` = `file://CMakeLists.txt`, `file://emulator`, `file://rpi-app` через `FILESEXTRAPATHS`
  с корнем репозитория. В образ попадает тот код, что в checkout, без отдельного `SRCREV`.
  **Не `externalsrc`:** когда каталог сборки (`build/yocto`) в том же git-репозитории, что и
  исходники, `externalsrc` хэширует весь корень рекурсивно — с `build/yocto`, клонами poky/meta-oe
  и `.yocto-cache` (десятки GB); видно по предупреждениям `Unable to get checksum ... hashserve.sock`.
- **libgpiod без ptest:** poky включает `ptest`, и libgpiod тогда собирает тесты с `glib-2.0`,
  `catch2`, `util-linux`, `libedit`. `PTEST_ENABLED:pn-libgpiod = "0"` в `kas.yml`.
- **libgpiod v2:** `periph` линкуется с C++-биндингами libgpiod v2, в poky их нет. Берутся из
  `meta-oe` (`libgpiod_2.1.3`, `cxx` включён по умолчанию). У meta-openembedded нет релизных тегов:
  закреплён последний коммит `scarthgap` до даты `yocto-5.0.20`; обновлять вместе с poky.
- **vcan:** в ядре `qemux86-64` CAN нет вовсе, а `features/can/can.scc` из kernel-cache тянет
  десяток драйверов модулями. Вместо него `linux-yocto_%.bbappend` + `vcan.cfg`: `CAN`, `CAN_RAW`,
  `CAN_DEV`, `CAN_VCAN` встроены в ядро, модуль грузить не нужно.
- **Автозапуск:** в образе sysvinit (`INIT: version 3.04`), поэтому init-скрипт через `update-rc.d`
  (`S90edge`): создаёт `vcan0` (`iproute2`), поднимает и запускает `edge vcan0` с выводом
  в `/dev/console`. Пакет добавлен в образ через `IMAGE_INSTALL:append` в `kas.yml`.
- **Проверка:** `edge` печатает `edge: listening on vcan0`, когда открыл интерфейс; `image.yml`
  передаёт эту строку в `run-qemu.sh` как `BOOT_EXPECT` и ждёт её вместе с `login:`.
- **Дальше:** см. следующие два раздела: сценарии в образе (#25) и полный стенд (#26).

## Сценарии в образе (#25)

Статус: **работает.** Прогон `image.yml` `40196683176` (коммит `4ef1139`): оба сценария
`tests/e2e/*.json` прошли с edge внутри образа, шаг занял 9 с; лог — артефакт `e2e-qemu-logs`.
Сборка образа 17 мин, весь прогон 23 мин.

Те же сценарии, что гоняет `make e2e` на хосте, с `EDGE=qemu`: `ci/stand.py` поднимает брокер на раннере,
`ci/stand-edge.sh` загружает образ через `yocto/run-qemu.sh`, и проверка та же: брокер увидел ровно
то, что отправил сценарий (формат — [TESTING.md](TESTING.md)).

- **Конфиг в гостя** — `-fw_cfg name=opt/mes/edge.conf` и `opt/mes/ca.crt` (по файлу на запись из
  `QEMU_FWCFG_DIR`). Нужно `CONFIG_FW_CFG_SYSFS=y`, которого в `qemux86-64` нет: фрагмент `fw_cfg.cfg`
  рядом с `vcan.cfg`. `edge.init` копирует файлы из `/sys/firmware/qemu_fw_cfg/by_name/opt/mes/*/raw`
  в `/etc/edge`; без них `edge` стартует по-старому (только CAN), поэтому строка
  `edge: listening on vcan0` в `image.yml` не зависит от стенда.
- **Кадры** — pty эмулятора (`QEMU_UART`) становится в госте дополнительным последовательным портом:
  явное устройство `isa-serial` на порту ввода-вывода `0x2e8`, а не ещё один `-serial`. Разбор
  `boot.log` показал, как `runqemu` запускает этот образ: `-serial mon:stdio -serial null`,
  `console=ttyS0 console=ttyS1`, ядро регистрирует только `ttyS0` и `ttyS1`. На `ttyS1` может висеть
  getty, и приглашение логина попало бы в поток кадров. Какой номер `ttyS` ядро даст порту `0x2e8`,
  из лога не вывести, поэтому `edge.init` ищет tty по адресу в `/sys/class/tty/ttyS*/port` (sysfs
  печатает его заглавными, `0x2E8`); в прогоне это оказался `/dev/ttyS3`.
- **Сеть** — slirp, хост для гостя `10.0.2.2`; он указан в `edge.conf` и в SAN сертификата сервера.
  Часы гостя совпали с хостовыми, и сертификат (срок 1 день) прошёл проверку: отдельной синхронизации
  времени не понадобилось.
- **Повтор** — `edge` выходит, если не может подключиться, поэтому `edge.init` гоняет его в цикле с
  паузой 2 с; иначе при брокере, который поднялся позже гостя, сервис остался бы мёртвым до конца загрузки.
- **Образ как артефакт** — `image.yml` публикует `yocto-image` (bzImage, rootfs в zstd,
  `revisions.txt`, `SHA256SUMS`; 31 МиБ, 14 дней). `IMAGE_DIR=<каталог>` в `run-qemu.sh` грузит его
  обычным `qemu-system-x86_64` хоста, без kas и дерева Yocto, с `-snapshot`, чтобы образ не менялся.
- **Запуск `image.yml`** — теперь ещё и по push в `main`, но только если менялось то, что попадает
  в образ или в его проверку (`yocto/`, `rpi-app/`, интерфейсы `emulator/`, CMake, стенд, сценарии,
  раннер). Группа `concurrency: image` без отмены: два параллельных прогона сохраняли бы по ~7 GB

## Полный стенд (#26)

Статус: **работает.** `stand.yml`, прогон `40198477887`: образ в QEMU, брокер, эмулятор-CLI и
Android-эмулятор с приложением; оба сценария зелёные за 2 мин, приложение подключилось к брокеру
по TLS и сохранило `[1001], seq=471`. Отчёт — артефакт `stand-report`, всё для повторного запуска —
`stand-bundle` (образ + APK + `revisions.txt` + `SHA256SUMS`, 52 МиБ, 14 дней).

**Что делает `stand.yml`** (после зелёного `image.yml` или вручную с `image_run=<id>`): скачивает
`yocto-image` и проверяет суммы, собирает закреплённое приложение, поднимает Android-эмулятор (те же
action и параметры, что в инструментальных тестах приложения: API 35, `google_apis`, x86_64) и запускает
`ci/stand.py run --android <apk> tests/e2e/*.json` с `EDGE=qemu`. Для каждого сценария проверяется вся
цепочка: эмулятор → edge в образе → брокер → приложение. Приложение для этого получает адрес брокера,
логин и CA из каталога `<externalFilesDir>/stand/` (`broker.properties`, `ca.crt`; их кладёт `adb push`),
после чего само включает MQTT; без этих файлов оно работает как обычно. Данные приложения перед каждым
сценарием стираются (`pm clear`), иначе дедупликация по `(deviceSerial, sequence)` отбросила бы повторную
отправку того же вектора. Ожидание от приложения — строка `Телеметрия сохранена от бойца [userId], seq=N`
в `logcat` для каждого валидного TELEMETRY-кадра.

Скриншот `app.png` — для человека, а не доказательство: он показывает режим связи (`СВЯЗЬ: ЭФИР (MQTT)`),
но значения на карте могут быть не от нашего кадра. `TelemetryViewModel` запускает имитатор в конструкторе,
раньше, чем `MapFragment` переключает режим на MQTT, и свежие записи имитатора перекрывают на экране
кадр вектора (его timestamp из 2024 года): на скриншоте прогона `stand.yml` `40199796377` пульс 75
и 36.6 °C при `pulseBpm=84` и `temperatureX100=3672` в кадре. Приём подтверждает только строка в `logcat`.

### Поднять стенд у себя: `make fullstand`

```bash
gh auth login                  # один раз; артефакты скачиваются через gh
make fullstand                 # последний успешный stand-bundle
make fullstand RUN=<id>        # конкретный прогон stand.yml
ANDROID=skip make fullstand    # без приложения
STAND_TIMEOUT=600 make fullstand   # там, где QEMU медленный
```

Ничего не собирается: скрипт скачивает бандл, проверяет `SHA256SUMS`, сообщает, чем ревизии бандла
отличаются от вашего checkout, и прогоняет сценарии на образе из бандла. Результат — `build/stand/junit.xml`
и `build/stand/<сценарий>/` (логи, `expected.txt`/`received.txt`, `logcat.txt` и `app.png`, если участвовало
приложение).

| Что нужно | Linux | macOS |
|---|---|---|
| `gh`, `python3`, `openssl`, `zstd` | apt | brew (`gh`, `zstd`), остальное системное |
| QEMU | `apt install qemu-system-x86` | `brew install qemu` |
| брокер | `apt install mosquitto mosquitto-clients` | `brew install mosquitto` |
| Android (по желанию) | эмулятор из Android SDK, виден через `adb devices` | то же, образ arm64 |

Без KVM (на Mac всегда) QEMU идёт в TCG; на Apple silicon образ из бандла загружается за секунды, и оба
сценария проходят за ~6 с каждый. Брокер `mosquitto` лежит в `sbin` (`/opt/homebrew/sbin`), которого нет в
`PATH`: скрипты ищут его там сами.

**Проверено на Mac** (Apple silicon, Homebrew QEMU 11.1.2): `make fullstand RUN=40198477887 ANDROID=skip`,
оба сценария зелёные. **Не проверено на Mac:** часть с Android (на этой машине нет Android SDK); её
проверяет `stand.yml`. Второй участник команды ещё не повторял инструкцию, поэтому критерий #26
«второй участник поднимает стенд по инструкции» остаётся за ним.

### Показать стенд: `make demo`

`make fullstand` прогоняет сценарии и гасит всё, поэтому для показа есть `make demo` (`ci/demo.py`): тот же брокер,
тот же `ci/stand-edge.sh` (edge в образе или на хосте) и то же приложение, но стенд остаётся поднятым и
управляется из одного приглашения. Он сам определяет, что есть на машине (образ и QEMU, Android-эмулятор) и при
сбое части продолжает без неё. Брокер слушает только `127.0.0.1` (`STAND_BIND` в `emulator/stand/lib.sh`), приложение
трогается только на эмуляторе. Руководство, матрица режимов и сценарий показа — [DEMO.md](DEMO.md); сквозную
проверку без клавиатуры (`make demo-check`: кадр, битый кадр, кадр) гоняет `make docker-check`.
