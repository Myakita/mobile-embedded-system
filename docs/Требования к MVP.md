# Требования к мобильному приложению мониторинга многоканальной телеметрической сети

## 1. Описание предметной области

Предметная область представляет собой распределённую систему мониторинга пользователей, оснащённых автономными телеметрическими устройствами.

Каждое устройство собирает и передаёт набор данных о состоянии пользователя и его положении:

- серийный номер устройства;
- идентификатор пользователя;
- температуру;
- пульс;
- систолическое и диастолическое давление;
- координаты;
- направление движения;
- качество рассчитанной позиции.

Положение формируется на стороне устройства на основе данных GNSS и IMU и передаётся в приложение как готовый результат.

Система поддерживает двунаправленный обмен двумя типами прикладных сообщений:

```text
TELEMETRY
COMMAND
```

Телеметрия передаётся от нижестоящих пользователей к разрешённым вышестоящим получателям. Команды передаются в обратном направлении — от разрешённого вышестоящего пользователя к допустимому нижестоящему получателю.

Пользователи объединяются в настраиваемую иерархическую структуру. Семантика этой иерархии хранится в мобильном приложении. Устройство не обязано хранить сведения о роли пользователя, названии подразделения или положении пользователя в организационной структуре.

Приложение должно позволять создавать и изменять эту иерархию, определять разрешённые направления обмена и на основании неё автоматически формировать MQTT publish/subscribe rules.

Сеть является многоканальной. Передача данных может выполняться через:

```text
LoRa
Wi‑Fi
LTE
```

LoRa используется как автономный радиоканал между устройствами. Wi‑Fi и LTE используются как IP-каналы для MQTT. Один и тот же логический пакет должен сохранять идентификаторы источника, получателя и последовательности независимо от используемого транспорта.

Система может содержать несколько независимых мультисетей. Каждая мультисеть имеет собственные:

- пользователей;
- устройства;
- иерархию;
- MQTT namespace;
- настройки сети;
- настройки шифрования;
- историю телеметрии;
- набор сохранённых карт.

Мобильное приложение выполняет роль основного пользовательского интерфейса системы. Через него пользователь должен:

- создавать и настраивать мультисети;
- регистрировать устройства;
- привязывать устройства к пользователям;
- строить и изменять иерархию;
- настраивать направления TELEMETRY и COMMAND;
- настраивать MQTT;
- настраивать периферию и сетевые интерфейсы устройств;
- выбирать профиль шифрования на стороне приложения-получателя;
- просматривать актуальную и историческую телеметрию;
- просматривать пользователей на карте;
- работать с offline-картами;
- отправлять разрешённые команды.

Параметры шифрования на устройстве и в мобильном приложении задаются независимо. Приложение-получатель должно использовать заранее настроенный профиль шифрования, соответствующий конфигурации устройства.

Обязательная целевая платформа мобильного приложения:

```text
Android
Java
Android SDK
MapLibre Native
```

# Требования к мобильному приложению мониторинга многоканальной телеметрической сети

## 1. Назначение продукта

Мобильное приложение предназначено для настройки, мониторинга и управления группой автономных телеметрических устройств, объединённых в единую многоканальную сеть.

Приложение должно обеспечивать:

- регистрацию и настройку устройств;
- привязку устройств к пользователям;
- построение иерархии пользователей;
- формирование правил обмена данными между уровнями иерархии;
- просмотр телеметрии;
- просмотр местоположения пользователей;
- просмотр направления движения;
- отображение текущего состояния связи;
- передачу разрешённых команд нижестоящим пользователям;
- конфигурирование сетевых интерфейсов устройств;
- конфигурирование источников телеметрии;
- настройку шифрования на стороне приложения-получателя;
- работу с несколькими независимыми мультисетями;
- работу при отсутствии доступа к Интернету, если данные поступают по доступному каналу.

Обязательная целевая платформа продукта:

```text
Android
Java
Android SDK
MapLibre Native
```

---

# 2. Основные сущности продукта

Пользователь приложения взаимодействует со следующими сущностями:

```text
Мультисеть
Пользователь
Устройство
Узел иерархии
Телеметрия
Команда
Профиль шифрования
Карта
```

---

# 3. Пользовательские роли

### 1.1. Оператор приложения

Пользователь приложения должен иметь возможность:

- создавать мультисеть;
- добавлять пользователей;
- добавлять устройства;
- связывать пользователя и устройство;
- формировать иерархию;
- назначать разрешённые направления передачи телеметрии;
- назначать разрешённые направления передачи команд;
- просматривать текущую телеметрию;
- просматривать положение пользователей;
- просматривать историю телеметрии;
- просматривать состояние устройств;
- отправлять разрешённые команды;
- настраивать устройства;
- настраивать сетевые интерфейсы;
- настраивать параметры шифрования.

---

# 4. Пользовательские требования

### 1.2. Создание мультисети

Пользователь должен иметь возможность создать новую независимую мультисеть.

При создании пользователь должен иметь возможность задать:

- отображаемое название сети;
- уникальный идентификатор сети;
- параметры MQTT;
- параметры шифрования приложения;
- настройки карты;
- настройки хранения истории;
- правила актуальности телеметрии.

После создания мультисеть должна отображаться в списке доступных сетей.

---

### 1.3. Переключение между мультисетями

Пользователь должен иметь возможность переключаться между несколькими независимыми мультисетями.

При переключении должны одновременно переключаться:

- список пользователей;
- список устройств;
- иерархия;
- MQTT-конфигурация;
- карта;
- профили шифрования;
- телеметрическая история;
- правила доступа.

Данные разных мультисетей не должны отображаться совместно без явного действия пользователя.

---

### 1.4. Добавление пользователя

Пользователь приложения должен иметь возможность создать карточку пользователя.

Карточка должна содержать минимум:

- идентификатор пользователя;
- отображаемое имя;
- привязанное устройство;
- положение в иерархии;
- текущее состояние;
- время последней телеметрии.

---

### 1.5. Добавление устройства

Пользователь должен иметь возможность зарегистрировать устройство в выбранной мультисети.

Для устройства должны отображаться минимум:

- серийный номер;
- идентификатор привязанного пользователя;
- версия протокола;
- состояние связи;
- время последнего сообщения;
- доступные интерфейсы;
- состояние шифрования;
- состояние источников телеметрии.

---

### 1.6. Привязка устройства к пользователю

Пользователь должен иметь возможность привязать одно устройство к выбранному пользователю.

После привязки телеметрия от данного устройства должна отображаться в карточке соответствующего пользователя.

Приложение должно предупреждать о конфликте, если устройство уже привязано к другому пользователю в той же мультисети.

---

### 1.7. Изменение привязки

Пользователь должен иметь возможность переназначить устройство другому пользователю.

После изменения:

- новая телеметрия должна относиться к новому пользователю;
- старая история не должна автоматически переписываться на нового пользователя;
- приложение должно явно показывать факт изменения привязки.

---

# 5. Требования к иерархии

### 1.8. Создание иерархии

Пользователь должен иметь возможность вручную построить иерархию пользователей.

Иерархия должна отображаться в виде дерева.

Пример:

```text
Уровень 1
   │
   ├── Уровень 2
   │      ├── Пользователь A
   │      └── Пользователь B
   │
   └── Уровень 3
          └── Пользователь C
```

---

### 1.9. Редактирование иерархии

Пользователь должен иметь возможность:

- создавать узел;
- удалять узел;
- переименовывать узел;
- перемещать узел;
- назначать родительский узел;
- перемещать пользователя;
- удалять пользователя из иерархии.

Изменение иерархии не должно требовать перепрошивки устройства.

---

### 1.10. Иерархическое направление телеметрии

Пользователь должен иметь возможность определить, кому конкретный пользователь отправляет телеметрию.

Приложение должно позволять выбрать:

```text
Источник → Получатель
```

для каждого участника сети.

Устройство не должно требовать хранения текстового описания подразделения или роли.

---

### 1.11. Иерархическое направление команд

Пользователь должен иметь возможность определить, каким нижестоящим пользователям конкретный пользователь имеет право отправлять команды.

Приложение должно запрещать отправку команды, если такая связь не разрешена конфигурацией.

---

### 1.12. Автоматическое обновление правил обмена

После изменения иерархии приложение должно пересчитать:

- допустимых получателей телеметрии;
- допустимых получателей команд;
- MQTT publish topics;
- MQTT subscribe topics.

Пользователь не должен вручную пересобирать все топики после каждого изменения дерева.

---

# 6. Требования к телеметрии

### 1.13. Приём телеметрии

Приложение должно принимать телеметрические сообщения от зарегистрированных устройств.

Телеметрический пакет содержит:

```text
version
messageType
flags
ttl
sequence
timestamp

deviceSerial
userId
destinationId

temperature_x100
pulse_bpm
pressure_sys
pressure_dia

latitude_e7
longitude_e7
heading_cdeg
positionQuality
```

---

### 1.14. Отображение температуры

Приложение должно отображать температуру пользователя в градусах Цельсия.

Значение:

```text
temperature_x100 = 3672
```

должно отображаться как:

```text
36.72 °C
```

---

### 1.15. Отображение пульса

Приложение должно отображать значение пульса в ударах в минуту.

---

### 1.16. Отображение давления

Приложение должно отображать:

- систолическое давление;
- диастолическое давление.

Формат отображения:

```text
120 / 80
```

---

### 1.17. Отображение положения

Приложение должно отображать последнее принятое положение пользователя.

Позиция поступает в виде:

```text
latitude_e7
longitude_e7
```

и должна быть преобразована в координаты для отображения на карте.

---

### 1.18. Отображение направления

Приложение должно отображать направление движения пользователя.

Источник:

```text
heading_cdeg
```

На карте ориентация маркера должна соответствовать полученному направлению.

---

### 1.19. Качество позиции

Приложение должно отображать качество рассчитанной позиции.

`positionQuality` должен отображаться в пользовательском виде, например:

```text
Хорошее
Ограниченное
Низкое
Недоступно
```

---

### 1.20. Время последней телеметрии

Для каждого пользователя должно отображаться время последнего полученного телеметрического сообщения.

---

### 1.21. Актуальность данных

Приложение должно отличать актуальную телеметрию от устаревшей.

Минимальные состояния:

```text
Актуально
Устарело
Нет данных
```

Порог перехода в состояние `Устарело` должен настраиваться для мультисети.

---

### 1.22. История телеметрии

Пользователь должен иметь возможность открыть историю телеметрии конкретного пользователя.

История должна содержать:

- время;
- температуру;
- пульс;
- давление;
- координаты;
- направление;
- качество позиции.

---

# 7. Требования к карте

### 1.23. Основной экран карты

Приложение должно иметь экран карты на базе MapLibre Native.

На карте должны отображаться пользователи, для которых доступно положение.

---

### 1.24. Маркер пользователя

Маркер пользователя должен позволять определить:

- положение;
- направление движения;
- состояние актуальности;
- выбран ли пользователь;
- время последнего обновления.

---

### 1.25. Поворот маркера

Маркер должен поворачиваться согласно `heading_cdeg`.

---

### 1.26. Выбор пользователя на карте

При нажатии на маркер должна открываться краткая карточка пользователя.

Карточка должна показывать минимум:

```text
Имя
Устройство
Температура
Пульс
Давление
Время обновления
Качество позиции
```

---

### 1.27. Переход в подробную карточку

Из карты пользователь должен иметь возможность перейти в подробную карточку выбранного пользователя.

---

### 1.28. История перемещений

Приложение должно иметь возможность отображать историю полученных координат пользователя в виде трека.

---

### 1.29. Ограничение истории трека

Пользователь должен иметь возможность выбрать отображаемый интервал истории, например:

```text
последние 10 минут
последний час
последние 24 часа
```

---

### 1.30. Offline-карта

Приложение должно позволять заранее сохранить выбранный регион карты для работы без Интернет-доступа.

---

### 1.31. Управление offline-регионами

Пользователь должен иметь возможность:

- выбрать область;
- начать загрузку;
- видеть прогресс;
- видеть размер;
- удалить сохранённую область;
- просмотреть список доступных offline-регионов.

---

### 1.32. Работа карты без Интернета

Если Интернет недоступен, но offline-карта сохранена, приложение должно продолжать:

- отображать карту;
- принимать телеметрию через доступный канал;
- обновлять положения пользователей;
- отображать направление.

---

# 8. Требования к командам

### 1.33. Двунаправленный формат сообщений

Телеметрия и команды должны использовать один логический формат пакета.

Поле:

```text
messageType
```

определяет назначение сообщения.

Допустимые значения:

```text
TELEMETRY
COMMAND
```

---

### 1.34. Формирование команды

Пользователь должен иметь возможность выбрать разрешённого получателя и сформировать командное сообщение.

Командное сообщение должно содержать:

```text
messageType = COMMAND
commandType
source
destination
sequence
timestamp
```

---

### 1.35. Доступность команд

Приложение должно показывать пользователю только те команды и получателей, которые разрешены текущей конфигурацией.

---

### 1.36. Подтверждение отправки

Перед отправкой команды приложение должно отображать:

- получателя;
- выбранную команду.

Пользователь должен явно подтвердить отправку.

---

### 1.37. Статус отправки команды

После отправки приложение должно отображать состояние:

```text
Создано
Передано
Подтверждено
Ошибка
```

если соответствующая информация доступна от транспортного уровня.

---

# 9. Требования к MQTT

### 1.38. Поддержка единого MQTT namespace

В рамках одной мультисети приложение должно использовать единое настраиваемое MQTT-пространство.

Отдельные локальные MQTT namespace не требуются.

---

### 1.39. Настройка корневого topic

Пользователь должен иметь возможность задать:

```text
network_root
```

для мультисети.

---

### 1.40. Иерархическая структура MQTT

Приложение должно формировать MQTT topics на основе текущей иерархии.

Рекомендуемый шаблон:

```text
<network_root>/<hierarchy_path>/<message_type>/to/<destination_id>/from/<source_id>
```

---

### 1.41. Автоматическое формирование topic

Пользователь не должен вручную создавать полный MQTT topic для каждого участника.

Приложение должно формировать topic автоматически на основании:

- мультисети;
- положения в иерархии;
- источника;
- получателя;
- типа сообщения.

---

### 1.42. Ручное редактирование MQTT

Для администратора/настройщика приложение должно позволять вручную изменить MQTT-параметры мультисети.

Минимум:

```text
broker
port
network_root
TLS
credentials
```

---

### 1.43. MQTT подписки

Приложение должно автоматически подписываться на топики, разрешённые пользователю текущей конфигурацией.

---

### 1.44. Восстановление подписок

После переподключения приложение должно автоматически восстановить необходимые MQTT-подписки.

---

### 1.45. Работа после смены сети

Переключение телефона:

```text
Wi‑Fi → LTE
LTE → Wi‑Fi
```

не должно требовать ручного повторного подключения пользователя к мультисети.

---

# 10. Требования к подключению и состоянию сети

### 1.46. Состояние MQTT

Приложение должно отображать состояние подключения:

```text
Подключено
Подключение
Отключено
Ошибка
```

---

### 1.47. Состояние канала

Для зарегистрированного устройства приложение должно иметь возможность отображать известное состояние его интерфейсов:

```text
LoRa
Wi‑Fi
LTE
```

если такая диагностическая информация поступает от устройства.

---

### 1.48. Потеря подключения

При временной потере связи приложение не должно удалять уже полученную телеметрию.

---

### 1.49. Восстановление соединения

После восстановления IP-соединения приложение должно автоматически попытаться восстановить MQTT-соединение.

---

# 11. Требования к конфигурации устройств

### 1.50. Режим конфигурирования

Пользователь должен иметь возможность перевести выбранное устройство в режим конфигурирования через предусмотренный локальный интерфейс.

---

### 1.51. Настройка пользователя устройства

Приложение должно позволять передать на устройство:

```text
userId
defaultDestinationId
allowedDestinationIds
```

---

### 1.52. Настройка телеметрии

Пользователь должен иметь возможность включать/выключать:

```text
Температура
Пульс
Давление
GNSS
IMU
```

---

### 1.53. Период телеметрии

Пользователь должен иметь возможность задавать период формирования и передачи телеметрии в пределах допустимого устройством диапазона.

---

### 1.54. Настройка LoRa

Приложение должно позволять изменять предусмотренные устройством параметры LoRa.

Доступность конкретных параметров должна определяться возможностями подключённого устройства.

---

### 1.55. Настройка Wi‑Fi

Приложение должно позволять задавать параметры Wi‑Fi устройства, если Wi‑Fi поддерживается устройством.

---

### 1.56. Настройка LTE

Приложение должно позволять задавать предусмотренные устройством параметры LTE-подключения, например профиль подключения/APN, если это поддерживается устройством.

---

### 1.57. Настройка MQTT устройства

Приложение должно передавать устройству MQTT-конфигурацию, рассчитанную из текущей мультисети и иерархии.

---

### 1.58. Применение конфигурации

После передачи настроек приложение должно явно показать результат:

```text
Применено
Не применено
Ошибка
Ожидает применения
```

---

### 1.59. Несинхронизированная конфигурация

Если настройки в приложении отличаются от подтверждённой конфигурации устройства, устройство должно отображаться как:

```text
Требует обновления конфигурации
```

---

# 12. Требования к шифрованию

### 1.60. Выбор профиля шифрования

Пользователь должен иметь возможность создать профиль шифрования для выбранной мультисети или устройства.

---

### 1.61. Независимая настройка сторон

Приложение должно учитывать, что параметры шифрования на устройстве задаются отдельно.

Настройка шифрования в мобильном приложении не должна автоматически считаться применённой на устройстве.

---

### 1.62. Выбор алгоритма

Пользователь должен иметь возможность выбрать один из поддерживаемых стандартных алгоритмов шифрования.

Набор алгоритмов должен быть ограничен поддерживаемыми приложением вариантами.

Пример допустимых профилей:

```text
AES-128-GCM
AES-256-GCM
ChaCha20-Poly1305
```

---

### 1.63. Ввод ключа

Пользователь должен иметь возможность вручную ввести или импортировать ключ для receiver-приложения.

---

### 1.64. Идентификатор ключа

Профиль должен содержать:

```text
Key ID
```

чтобы приложение могло определить, какой ключ использовать для конкретного сообщения.

---

### 1.65. Привязка профиля

Пользователь должен иметь возможность связать CryptoProfile:

- с мультисетью;
- с конкретным устройством;
- с разрешённой группой устройств.

---

### 1.66. Ошибка расшифрования

Если приложение не может расшифровать пакет, пользователь должен видеть понятный статус, например:

```text
Нет подходящего ключа
Ошибка расшифрования
Ошибка проверки целостности
Неподдерживаемый алгоритм
```

---

### 1.67. Хранение ключей

После сохранения секретный ключ не должен постоянно отображаться в интерфейсе приложения.

---

### 1.68. Удаление ключа

Пользователь должен иметь возможность удалить CryptoProfile.

После удаления приложение должно перестать расшифровывать сообщения, требующие этот профиль.

---

### 1.69. Независимость шифрования от транспорта

Одинаковый защищённый payload должен приниматься приложением независимо от того, через какой канал он был доставлен:

```text
LoRa → шлюз → MQTT
Wi‑Fi → MQTT
LTE → MQTT
```

---

# 13. Требования к безопасности продукта

### 1.70. Защита секретов

Секретные ключи не должны храниться в открытом виде в обычных файлах настроек приложения.

---

### 1.71. Проверка целостности

Приложение не должно отображать пакет как корректную телеметрию, если проверка целостности завершилась ошибкой.

---

### 1.72. Изоляция мультисетей

Ключи, пользователи, устройства и телеметрия одной мультисети не должны автоматически использоваться в другой.

---

### 1.73. Неизвестные сообщения

Неизвестный или повреждённый пакет не должен приводить к завершению работы приложения.

---

# 14. Требования к обнаружению дублей

### 1.74. Уникальность сообщения

Приложение должно использовать:

```text
deviceSerial + sequence
```

для определения уникальности сообщения.

---

### 1.75. Удаление дублей

Если одна и та же телеметрия поступила несколько раз через разные каналы, она должна быть обработана как одно логическое сообщение.

---

### 1.76. История дублей

Повторный пакет не должен создавать вторую запись телеметрии в пользовательской истории.

---

# 15. Требования к карточке пользователя

### 1.77. Сводная карточка

Карточка пользователя должна содержать:

```text
Имя
User ID
Device Serial
Статус
Последнее обновление
```

---

### 1.78. Телеметрия в карточке

Карточка должна показывать:

```text
Температура
Пульс
Давление
```

---

### 1.79. Навигация в карточке

Карточка должна показывать:

```text
Координаты
Направление
Качество позиции
Время координаты
```

---

### 1.80. Переход на карту

Из карточки пользователя должна быть возможность открыть карту с выбранным пользователем в центре.

---

# 16. Требования к списку пользователей

### 1.81. Общий список

Приложение должно показывать список доступных пользователю участников текущей мультисети.

---

### 1.82. Состояние в списке

Для каждого пользователя должен отображаться минимум:

```text
Имя
Статус
Последнее обновление
```

---

### 1.83. Поиск

Пользователь должен иметь возможность найти участника по:

- отображаемому имени;
- User ID;
- Device Serial.

---

### 1.84. Фильтрация

Пользователь должен иметь возможность фильтровать список минимум по:

```text
Онлайн
Нет связи
Есть актуальная телеметрия
Телеметрия устарела
```

---

# 17. Требования к состоянию устройства

### 1.85. Состояние устройства

Приложение должно различать минимум:

```text
ONLINE
OFFLINE
UNKNOWN
CONFIGURATION_REQUIRED
```

---

### 1.86. Last Seen

Для каждого устройства должно отображаться время последнего принятого сообщения.

---

# 18. Требования к уведомлениям

### 1.87. Потеря связи

Приложение должно иметь настройку уведомления при длительной потере связи с выбранным устройством.

---

### 1.88. Восстановление связи

Приложение должно иметь возможность уведомлять пользователя о восстановлении связи.

---

### 1.89. Новая команда

Если приложение выступает получателем команд, новая команда должна отображаться как отдельное событие интерфейса.

---

# 19. Требования к сохранению данных

### 1.90. Локальное хранение

Приложение должно сохранять:

- мультисети;
- пользователей;
- устройства;
- иерархию;
- MQTT-настройки;
- настройки отображения;
- историю телеметрии;
- метаданные CryptoProfile;
- метаданные offline-карт.

---

### 1.91. Сохранение после перезапуска

После закрытия и повторного запуска приложения ранее сохранённая конфигурация должна быть восстановлена.

---

### 1.92. Ограничение истории

Пользователь должен иметь возможность настроить максимальный срок хранения телеметрической истории.

---

### 1.93. Очистка истории

Пользователь должен иметь возможность удалить историю:

- конкретного пользователя;
- всей мультисети.

---

# 20. Требования к пользовательскому интерфейсу

### 1.94. Главный экран

Главный экран должен предоставлять быстрый доступ минимум к:

```text
Карта
Пользователи
Иерархия
Устройства
Команды
Настройки сети
```

---

### 1.95. Отображение активной мультисети

На основных экранах должно быть понятно, какая мультисеть сейчас выбрана.

---

### 1.96. Ошибки

Ошибка должна быть показана пользователю понятным текстом, а не только кодом исключения или внутренним идентификатором.

---

### 1.97. Подтверждение критичных изменений

Приложение должно запрашивать подтверждение перед:

- удалением устройства;
- удалением пользователя;
- удалением мультисети;
- удалением CryptoProfile;
- очисткой истории;
- отправкой команды.

---

# 21. Требования к диагностике

### 1.98. Диагностический экран

Приложение должно предоставлять диагностический экран.

---

### 1.99. MQTT диагностика

Должны отображаться:

```text
Broker
Connection state
Last reconnect
Active subscriptions
```

---

### 1.100. Диагностика пакетов

Должны отображаться счётчики:

```text
Принято пакетов
Принято TELEMETRY
Принято COMMAND
Отброшено дублей
Ошибок расшифрования
Ошибочных пакетов
```

---

### 1.101. Диагностика пользователя

Для выбранного пользователя должна быть возможность увидеть:

```text
Device Serial
Last Sequence
Last Timestamp
Last Seen
```

---

# 22. Требования к работе без Интернета

### 1.102. Offline UI

Приложение должно запускаться и показывать ранее сохранённые данные без доступа к Интернету.

---

### 1.103. Offline-карта

Сохранённые offline-регионы MapLibre должны оставаться доступными без сети.

---

### 1.104. Локальная история

Ранее сохранённая телеметрическая история должна быть доступна без подключения.

---

### 1.105. Отложенные изменения

Если устройство недоступно во время изменения конфигурации, приложение должно сохранить новое состояние как:

```text
Ожидает применения
```

а не считать настройку применённой.

---

# 23. Ограничения продукта

### 1.106. Платформа

Продукт должен работать на Android.

---

### 1.107. Язык реализации

Основной код мобильного приложения должен быть написан на Java.

---

### 1.108. Android SDK

Приложение должно использовать нативный Android SDK.

---

### 1.109. Карты

Для картографического интерфейса используется MapLibre Native.

---

### 1.110. Типы сетевых сообщений

Сетевой application layer содержит только:

```text
TELEMETRY
COMMAND
```

---

### 1.111. Единый payload

Для TELEMETRY и COMMAND используется один двунаправленный `LMash_Payload_t`.

---

### 1.112. Настраиваемая иерархия

Иерархия не должна быть жёстко зашита в приложение.

---

### 1.113. Настраиваемые MQTT topics

Структура MQTT namespace должна формироваться из настроек мультисети и текущей иерархии.

---

### 1.114. Независимость от конкретного транспорта

Пользовательская модель телеметрии не должна зависеть от того, был пакет доставлен через:

```text
LoRa
Wi‑Fi
LTE
```

---

# 25. Критерии готовности MVP

MVP считается функционально готовым, если пользователь может:

1. Создать мультисеть.
2. Настроить MQTT-соединение.
3. Добавить пользователей.
4. Добавить устройства.
5. Привязать устройство к пользователю.
6. Создать иерархию.
7. Настроить направление телеметрии.
8. Настроить разрешённое направление команд.
9. Получить `LMash_Payload_t`.
10. Распознать TELEMETRY.
11. Распознать COMMAND.
12. Расшифровать пакет по выбранному CryptoProfile.
13. Отбросить дубли.
14. Показать температуру.
15. Показать пульс.
16. Показать давление.
17. Показать положение.
18. Показать направление.
19. Показать качество позиции.
20. Показать пользователя на MapLibre.
21. Открыть карточку пользователя.
22. Отправить разрешённую команду.
23. Переключиться между Wi‑Fi и LTE без потери конфигурации.
24. Сохранить историю.
25. Открыть offline-карту.
26. Изменить конфигурацию устройства.
27. Увидеть, применена конфигурация или ожидает применения.
28. Перезапустить приложение без потери настроек.
