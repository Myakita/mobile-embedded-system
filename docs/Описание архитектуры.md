# Архитектура многоканальной телеметрической сети — v3

## 1. Назначение

Система строится как единая мультисеть с тремя независимыми каналами передачи:

- LoRa;
- Wi‑Fi;
- LTE.

Прикладной пакет один и тот же для всех каналов. Канал передачи меняется, но идентификаторы источника/получателя и смысл сообщения сохраняются.

В этой версии оставлены только два прикладных типа данных:

```text
TELEMETRY
COMMAND
```

Отдельные `event`, `config`, `response`, `route request` и другие прикладные сообщения не используются.

Конфигурация устройства, интерфейсов, MQTT-топиков, иерархии и прав выполняется через мобильное приложение.

---

# 2. Общая схема

```text
             Sensors / GNSS / IMU
                     │
                     ▼
              LMash_Payload_t
                     │
                     ▼
                  RouterD
             ┌───────┼───────┐
             │       │       │
             ▼       ▼       ▼
           LoRa    Wi‑Fi     LTE
             │       │       │
           LMesh    MQTT     MQTT
```

LoRa использует собственный компактный протокол поверх raw LoRa.

Wi‑Fi и LTE используют MQTT поверх IP.

---

# 3. Двунаправленный payload

Один `LMash_Payload_t` используется в обоих направлениях.

```text
нижестоящий узел
      │
      │ TELEMETRY
      ▼
вышестоящий узел

вышестоящий узел
      │
      │ COMMAND
      ▼
нижестоящий узел
```

`messageType` определяет, как интерпретировать пакет.

---

## 3.1. Тип сообщения

```c
typedef enum
{
    LMASH_MSG_TELEMETRY = 0u,
    LMASH_MSG_COMMAND   = 1u

} LMash_MessageType_t;
```

Для wire-format рекомендуется хранить значение в поле фиксированной ширины:

```c
uint8_t messageType;
```

а `enum` использовать как перечень допустимых значений. Это исключает зависимость размера передаваемого пакета от размера `enum` у конкретного компилятора.

---

## 3.2. Тип команды

Для безопасной учебной/небоевой реализации можно использовать нейтральный набор команд:

```c
typedef enum
{
    LMASH_CMD_NONE      = 0u,
    LMASH_CMD_CHECK_IN  = 1u,
    LMASH_CMD_HOLD      = 2u,
    LMASH_CMD_RETURN    = 3u

} LMash_CommandType_t;
```

В структуре передаётся:

```c
uint8_t commandType;
```

`commandType` имеет смысл только если:

```c
messageType == LMASH_MSG_COMMAND
```

Для телеметрии:

```c
commandType = LMASH_CMD_NONE;
```

---

## 3.3. Структура пакета

```c
typedef struct
{
    uint8_t  version;
    uint8_t  messageType;
    uint8_t  commandType;
    uint8_t  flags;

    uint8_t  ttl;

    uint32_t sequence;
    uint32_t timestamp;

    uint64_t deviceSerial;
    uint64_t userId;
    uint64_t destinationId;

    int16_t  temperature_x100;
    uint16_t pulse_bpm;

    uint8_t  pressure_sys;
    uint8_t  pressure_dia;

    int32_t  latitude_e7;
    int32_t  longitude_e7;

    uint16_t heading_cdeg;
    uint8_t  positionQuality;

} LMash_Payload_t;
```

---

# 4. Интерпретация пакета

## 4.1. TELEMETRY

```text
messageType = LMASH_MSG_TELEMETRY
commandType = LMASH_CMD_NONE
```

Используются:

```text
version
flags
ttl
sequence
timestamp

deviceSerial
userId
destinationId

temperature_x100
pulse_bpm
pressure_sys
pressure_dia

latitude_e7
longitude_e7
heading_cdeg
positionQuality
```

Положение формируется после объединения данных GNSS + IMU.

---

## 4.2. COMMAND

```text
messageType = LMASH_MSG_COMMAND
```

Используются:

```text
version
messageType
commandType
flags
ttl
sequence
timestamp

deviceSerial
userId
destinationId
```

Поля телеметрии в командном сообщении не интерпретируются.

Один и тот же payload остаётся фиксированным по структуре, поэтому парсеру не нужны разные C-структуры для разных направлений обмена.

---

# 5. Идентичность устройства

Устройство хранит:

```text
deviceSerial
userId
defaultDestinationId
```

Дополнительно конфигурация может содержать:

```text
allowedDestinationIds[]
```

На устройстве не требуется хранить текстовые названия организационных единиц или должностей.

---

# 6. Иерархия

Организационная иерархия задаётся мобильным приложением.

Логически:

```text
Level 1
   ↓
Level 2
   ↓
Level 3
   ↓
Level 4
```

Приложение знает:

```text
кто к какому уровню относится
кто может получать телеметрию
кто может отправлять разрешённые команды
какие MQTT-подписки назначить устройству
какой destinationId использовать
```

Устройство получает только готовую конфигурацию.

Например:

```text
my_id
user_id
default_destination_id

publish_topics[]
subscribe_topics[]
allowed_destination_ids[]
```

Устройство не обязано знать смысл уровней иерархии.

---

# 7. Направления обмена

Для телеметрии направление определяется конфигурацией мобильного приложения:

```text
нижний уровень
      │
      │ TELEMETRY
      ▼
следующий разрешённый уровень
```

Для команд:

```text
вышестоящий уровень
      │
      │ COMMAND
      ▼
разрешённый нижестоящий получатель
```

Контроль того, кто кому может отправлять COMMAND, находится в конфигурации/ACL, сформированной приложением.

---

# 8. MQTT

MQTT используется одновременно поверх:

```text
Wi‑Fi
LTE
```

Отдельных локальных MQTT namespace нет.

Вся система работает в одном настраиваемом пространстве мультисети.

---

# 9. Настраиваемая структура MQTT topics

Topic не должен быть жёстко зашит в прошивку.

Мобильное приложение формирует:

```text
network_root
hierarchy_path
publish_topic
subscribe_topics[]
```

Базовый шаблон:

```text
<network_root>/<hierarchy_path>/<message_type>/to/<destination_id>/from/<source_id>
```

---

## 9.1. Telemetry

Пример шаблона:

```text
<root>/<hierarchy>/telemetry/to/<dst>/from/<src>
```

Пример конкретного topic:

```text
mesh-a/7F10/21A0/0304/telemetry/to/7A831204/from/19AA0221
```

Для устройства:

```text
7F10/21A0/0304
```

— просто сконфигурированный путь.

Мобильное приложение знает его организационный смысл.

---

## 9.2. Command

Пример шаблона:

```text
<root>/<hierarchy>/command/to/<dst>/from/<src>
```

Например:

```text
mesh-a/7F10/21A0/0304/command/to/19AA0221/from/7A831204
```

Payload остаётся тем же:

```text
LMash_Payload_t
```

но:

```text
messageType = LMASH_MSG_COMMAND
```

---

# 10. MQTT-подписки

Устройство получает готовый список подписок от мобильного приложения.

Например:

```text
subscribe_topics[] =
{
    "mesh-a/.../telemetry/to/<my_id>/#",
    "mesh-a/.../command/to/<my_id>/#"
};
```

Или более широкие иерархические маски, если они разрешены политикой приложения.

Таким образом MQTT иерархия является настраиваемой частью мультисети.

---

# 11. Только два сетевых класса

В текущей версии используются только:

```text
telemetry
command
```

Итого namespace:

```text
<root>/<hierarchy>/telemetry/to/<dst>/from/<src>

<root>/<hierarchy>/command/to/<dst>/from/<src>
```

Это намеренно минимальная модель.

---

# 12. MQTT QoS

Предлагаемый базовый вариант:

| Тип | QoS |
|---|---:|
| `TELEMETRY` | 0 |
| `COMMAND` | 1 |

Телеметрия периодическая, поэтому потеря одного отдельного измерения обычно компенсируется следующим сообщением.

Командное сообщение требует более надёжной доставки.

При этом MQTT QoS не заменяет собственный `sequence`.

---

# 13. Дедупликация

Уникальность сообщения:

```text
MessageID = deviceSerial + sequence
```

Каждый промежуточный узел хранит небольшой cache недавно обработанных сообщений.

Например:

```text
19AA0221 : 101
19AA0221 : 102
19AA0221 : 103
```

Повтор:

```text
19AA0221 : 103
```

отбрасывается.

Это особенно важно при наличии нескольких каналов:

```text
LoRa
Wi‑Fi
LTE
```

---

# 14. LoRa

LoRa используется как автономный P2P/multi-hop transport.

```text
LoRa PHY
   ↓
LMesh
   ↓
LMash_Payload_t
```

Классический LoRaWAN не является обязательной частью этой архитектуры.

---

# 15. Минимальные сообщения LMesh

LMesh не выполняет динамический поиск маршрутов.

Минимально:

```text
HELLO
DATA
ACK
```

| Тип | Назначение |
|---|---|
| `HELLO` | Обнаружение доступного соседнего узла |
| `DATA` | Перенос `LMash_Payload_t` |
| `ACK` | Подтверждение сообщения, если оно требуется |

Нет:

```text
ROUTE_REQ
ROUTE_REPLY
ROUTE_ERROR
```

---

# 16. LoRa header

Транспортный заголовок может содержать:

```c
typedef struct
{
    uint8_t  version;
    uint8_t  type;
    uint8_t  flags;
    uint8_t  ttl;

    uint32_t originId;
    uint32_t destinationId;

    uint32_t previousHop;
    uint32_t nextHop;

    uint32_t sequence;
    uint8_t  payloadLength;

} LMesh_Header_t;
```

LoRa-пакет:

```text
┌──────────────────────┐
│ LMesh_Header_t       │
├──────────────────────┤
│ LMash_Payload_t      │
└──────────────────────┘
```

---

# 17. TTL

TTL ограничивает число ретрансляций:

```text
TTL = 4

A → B    TTL = 3
B → C    TTL = 2
C → D    TTL = 1
```

При:

```text
TTL == 0
```

пакет больше не ретранслируется.

---

# 18. LTE

LTE не имеет отдельного application payload.

Для RouterD LTE — IP-интерфейс:

```text
LTE modem
    │
    ▼
wwan0
    │
    ▼
IP
    │
    ▼
MQTT
    │
    ▼
LMash_Payload_t
```

Для Raspberry Pi предпочтителен LTE-модем через USB с управлением через MBIM/QMI/ModemManager.

---

# 19. Wi‑Fi

Wi‑Fi использует ту же MQTT-модель:

```text
LMash_Payload_t
       ↓
      MQTT
       ↓
       IP
       ↓
     Wi‑Fi
```

Различие между LTE и Wi‑Fi существует только на транспортном уровне.

---

# 20. RouterD

`RouterD` является единым узлом маршрутизации между интерфейсами:

```text
                   RouterD
              ┌──────┼──────┐
              │      │      │
             LoRa   Wi‑Fi   LTE
              │      │      │
            LMesh   MQTT    MQTT
```

RouterD выполняет:

- приём сообщения;
- проверку `MessageID`;
- выбор разрешённого transport edge;
- преобразование MQTT ↔ LMesh;
- TTL;
- deduplication;
- ACK;
- передачу неизменённого прикладного payload.

---

# 21. Пример перехода LoRa → LTE

```text
Node A
   │
 LoRa
   ▼
Node B
   │
 LTE
   ▼
Node C
```

A формирует:

```text
source      = A
destination = C
messageType = TELEMETRY
sequence    = 471
```

A → B:

```text
LMesh header
+
LMash_Payload_t
```

B извлекает payload и публикует:

```text
<configured-root>/<configured-hierarchy>/telemetry/to/C/from/A
```

через LTE.

При этом:

```text
deviceSerial
userId
destinationId
sequence
```

не меняются.

---

# 22. Пример обратного направления

```text
Node C
   │
 LTE
   ▼
Node B
   │
 LoRa
   ▼
Node A
```

C создаёт:

```text
messageType  = COMMAND
destinationId = A
```

MQTT:

```text
<configured-root>/<configured-hierarchy>/command/to/A/from/C
```

B получает пакет через MQTT и передаёт тот же `LMash_Payload_t` через LMesh/LoRa.

---

# 23. Мобильное приложение

Приложение является основным конфигуратором сети.

Оно задаёт:

```text
deviceSerial ↔ userId

network_root
hierarchy_path

default_destination_id
allowed_destination_ids[]

publish_topics[]
subscribe_topics[]

Wi‑Fi configuration
LTE configuration
LoRa configuration

sensor configuration
GNSS configuration
IMU configuration

telemetry period
protocol parameters
```

Также приложение хранит смысл иерархии и на его основе формирует разрешённые направления TELEMETRY/COMMAND.

---

```text
device:

    default_destination_id

mqtt:
    network_root

    telemetry_publish_topic

    gnss_enable
    sample_period
```

# 25. Основные принципы

1. Используется один двунаправленный `LMash_Payload_t`.
2. `messageType` определяет `TELEMETRY` или `COMMAND`.
3. Для wire-format значения enum передаются через фиксированные `uint8_t`.
4. В мультисети используются только два прикладных класса: telemetry и command.
5. Все MQTT topics настраиваются мобильным приложением.
6. Отдельных `local/...` MQTT topics нет.
7. MQTT namespace может быть иерархическим.
8. Устройство не интерпретирует смысл организационных уровней.
9. Мобильное приложение формирует иерархию, ACL и список подписок.
10. LoRa использует собственный LMesh.
11. LMesh не выполняет динамический поиск маршрутов.
12. LTE и Wi‑Fi используют MQTT.
13. `deviceSerial + sequence` используется для дедупликации.
14. Один и тот же payload может переходить LoRa ↔ Wi‑Fi ↔ LTE.
15. Промежуточный узел не становится новым источником сообщения.
