# Интеграционные тесты: состав, критерии, формат (#28)

Родительские задачи: [#4](https://github.com/Myakita/mobile-embedded-system/issues/4) (подход) и
[#5](https://github.com/Myakita/mobile-embedded-system/issues/5) (автоматизация). Как устроен CI —
в [CI.md](CI.md); здесь только то, что проверяют интеграционные тесты и как их описывать.

Статус каждого пункта указан явно: **есть** — работает в репозитории, **план** — описано здесь, кода
ещё нет. Документ — рабочий формат для исполнителей #29, #30, #32, #33; если формат мешает вашему
сценарию, правьте его в этом файле, а не обходите.

## Точки взаимодействия

```
мок JSON ──▶ emu> / cli.py run ──▶ UART (pty) ──▶ edge ──▶ брокер MQTT (TLS+ACL) ──▶ приложение
 IP-1                IP-2            IP-3          IP-4              IP-5
```

| ID | Граница | Что проходит | Статус |
|---|---|---|---|
| IP-1 | мок → `emulator/cli.py` | сценарий JSON, кодек `emulator/lmash_v1.py`, сверка `wireHex` с `protocol/vectors/` | есть (`emulator/tests/test_cli.py`) |
| IP-2 | `cli.py` → edge | 54 байта LMash v1 через pty (в образе — второй serial QEMU, `/dev/ttyS1`) | план (#22, #25) |
| IP-3 | edge → брокер | MQTT 8883, TLS, логин, QoS 1; топик `<root>/<path>/telemetry/to/<dst>/from/<src>` как в `MqttTopicBuilder` приложения | план (#22) |
| IP-4 | брокер → приложение | подписка приложения, разбор пакета (`LMashPayload`) | план (#5a, #26) |
| IP-5 | приложение → брокер → edge | COMMAND в обратную сторону | вне объёма этого этапа |

CAN, I²C и GPIO у `cli.py` есть как самостоятельные интерфейсы (`can.send`, `i2c.*`, `gpio.*`), но
полный пакет LMash в классический CAN-кадр (8 байт) не помещается, поэтому сквозной путь телеметрии
идёт через UART. Их проверка — отдельные сценарии эмулятор ↔ edge (#30).

## Формат сценария

Сценарий — это **существующий JSON-формат `emulator/cli.py`** без расширений: `devices`, `process`,
`events`. Новых полей нет, потому что `cli.validate` отвергает неизвестные ключи, а чужой CLI
мы не меняем. Что нужно знать:

- `devices` поднимает интерфейсы; путь pty каждого UART процесс получает в переменной
  `MES_UART_<ИМЯ>` (для порта `sensor` — `MES_UART_SENSOR`).
- `process` — команда, которую раннер запускает вместе с устройствами и чей stdout пишет в лог.
  В интеграционных сценариях это всегда `["bash", "ci/stand-edge.sh"]`: скрипт сам выбирает edge
  на хосте или внутри образа по переменной `EDGE=host|qemu`, поэтому **один и тот же сценарий
  идёт в обоих режимах**.
- `events` выполняются по порядку. `uart.send` подаёт данные, `stdout.expect` ждёт строку в выводе
  процесса (`timeout_ms`, по умолчанию 5000), `*.expect` сверяют регистры и линии.

Что не выразить на стороне `cli.py`, проверяет обёртка `ci/stand.sh`: **каждое** `uart.send` с пакетом
LMash должно дойти до брокера байт в байт. Обёртка берёт ожидаемые байты из самого сценария
(`cli.payload(event)`), подписывается на `<root>/#` до старта и сверяет число и содержимое
сообщений. Так сценарию не нужен отдельный блок «ожидания», и он не может разойтись с тем, что
реально отправлено. Негативным сценариям (#33), где на брокер **ничего** не должно дойти, обёртка
понадобится расширить; это делается рядом с их первым тестом, не заранее.

Минимальный пример (E2E-01):

```json
{
  "devices": {"uart": {"sensor": {}}},
  "process": ["bash", "ci/stand-edge.sh"],
  "events": [
    {"action": "stdout.expect", "text": "edge: connected to", "timeout_ms": 120000},
    {"action": "uart.send", "port": "sensor", "message": {"...": "поля из emulator/mocks/telemetry-v1.json"}},
    {"action": "stdout.expect", "text": "edge: published 54 bytes", "timeout_ms": 10000}
  ]
}
```

Файлы лежат в `tests/e2e/<ID>-<имя>.json`; новый сценарий — это новый файл, правок workflow не нужно.

## Запуск и отчёт

| Что | Команда | Статус |
|---|---|---|
| Все сценарии | `make e2e` | план (#31) |
| Один сценарий | `make e2e SCENARIO=tests/e2e/E2E-01-telemetry.json` | план (#31) |
| Режим edge | `EDGE=host` (по умолчанию, секунды) или `EDGE=qemu` (образ в QEMU, минуты) | план (#25) |
| Проверка локально на Mac | `make docker-check` (build + test + guard в ubuntu:24.04) | **есть** |

Код выхода: `0` — все сценарии прошли, `1` — хотя бы один упал. Сообщение об ошибке называет сценарий и
событие (`events[N] (action): ...`), как это уже делает `cli.py run`.

Отчёт — каталог `build/stand/`, в CI он выгружается артефактом:

```
build/stand/junit.xml            один <testcase> на сценарий
build/stand/<ID>/emu.log         вывод cli.py run
build/stand/<ID>/edge.log        stdout edge (в режиме qemu — boot.log с консолью гостя)
build/stand/<ID>/broker.log      лог mosquitto
build/stand/<ID>/expected.bin    байты, которые сценарий отправил
build/stand/<ID>/received.bin    байты, которые принял подписчик
```

## Состав тестов и критерии прохождения

Тест **падает** по таймауту, по расхождению байт и по ненулевому коду процесса; «не пришло ничего»
считается отказом, а не пропуском.

| ID | Проверка | Предусловия | Действие | PASS | Уровень | Кто | Статус |
|---|---|---|---|---|---|---|---|
| E2E-01 | телеметрия дошла | брокер с TLS+ACL, edge запущен | `uart.send` пакета из `telemetry-v1.json` | edge печатает `published 54 bytes`; подписчик получил ровно 54 байта = `wireHex`, топик соответствует схеме | host, qemu | #25 | план |
| BROKER-01 | ACL брокера | брокер стенда | чужой пользователь читает и пишет на `mes/smoke/#` | чужой не получает сообщений, посторонний publish не доставлен | `make stand` | #22 | есть (`emulator/stand/smoke.sh`) |
| STAND-01 | приложение приняло пакет | стенд из E2E-01 + Android-эмулятор с APK | та же отправка | в logcat приложения подключение и принятый пакет с ожидаемым `sequence` | stand.yml | #26 | план |

Остальные тесты — **предложение** по задачам-исполнителям; состав и ID уточняет тот, кто их делает,
критерии PASS пишутся в этой же таблице тем же образом:

## Уровни запуска

Один сценарий проходит несколько уровней; чем выше, тем дороже. Подробности CI — в [CI.md](CI.md).

| Уровень | Где | Когда |
|---|---|---|
| L0 | Mac нативно | перед коммитом: `python3 -m unittest discover -s emulator/tests -p 'test_cli.py'`, `ci/guard.py` |
| L1 | Docker `ubuntu:24.04` | перед коммитом: `make docker-check`, затем `EDGE=host make e2e` |
| L2 | `ci.yml` | каждый push |
| L3 | `full.yml` | тег `full-N`: устройства ядра и MQTT-стенд |
| L4 | `image.yml` | образ Yocto в QEMU и `EDGE=qemu make e2e` |
| L5 | `stand.yml` | весь стенд с Android-эмулятором, артефакты `stand-report` и `stand-bundle` |

L0–L1 дают быструю обратную связь, но финальным критерием остаются L4–L5: только там образ грузится
на KVM и видны расхождения amd64 и разницы Docker Desktop и Linux (таблица в `AGENTS.md`).
